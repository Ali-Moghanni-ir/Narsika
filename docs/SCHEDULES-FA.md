# راهنمای Scheduled Tasks در Narsika

نسخهٔ محلی Beta — ۲۰۲۶-۰۹-۱۴

بخش **Schedules** برای اجرای منظم Backup و Playbook روی دستگاه‌های فعلی Cisco و MikroTik ساخته شده است. هیچ برنامهٔ زمان‌بندی از پیش فعال نیست. نصب با فهرست خالی شروع می‌شود و دادهٔ نمایشی وارد محصول نمی‌شود.

## ساخت اولین Task

از منوی کناری، Schedules و سپس **New task** را باز کن:

1. **Operation:** نام Task و نوع کار را انتخاب کن. برای Playbook، فایل فعال و متغیرهای JSON را بررسی کن. متغیرهایی مانند `narsika_apply` رفتار Preview/Apply همان Playbook را تعیین می‌کنند؛ زمان‌بند خودش آن‌ها را فعال نمی‌کند.
2. **Targets:** دستگاه‌ها را انتخاب کن. فقط vendor سازگار نمایش داده می‌شود. جست‌وجو با نام، IP یا گروه ممکن است. اعضا ثابت‌اند؛ اضافه‌شدن دستگاه جدید به گروه آن را خودکار وارد Task نمی‌کند.
3. **Timing:** زمان‌بندی و منطقهٔ زمانی را تعیین کن. می‌توانی فعال‌سازی پس از ذخیره را خاموش کنی تا Task به‌صورت Paused ذخیره شود.
4. **Review:** نام عملیات، پارامترها، IP هدف‌ها، منطقهٔ زمانی و سه موعد بعدی را ببین. تأیید کن که اجراهای آینده ممکن است بدون پرسش مجدد تنظیمات دستگاه را تغییر دهند؛ سپس Save task را بزن.

پیش‌نمایش ده دقیقه اعتبار دارد. تغییر هدف، Credential یا فایل Playbook در این فاصله باعث رد ذخیره و درخواست بازبینی تازه می‌شود. رمزهای ارتباطی داخل Task به‌صورت plaintext نگه‌داری نمی‌شوند؛ متغیرها و هویت اتصال در تعریف رمزنگاری‌شده قرار می‌گیرند.

## انواع زمان‌بندی

| نوع | رفتار |
|---|---|
| One time | یک بار در تاریخ و ساعت آینده؛ پس از عبور از موعد غیرفعال می‌شود |
| Every few hours | هر ۱ تا ۷۲۰ ساعت سپری‌شده از زمان شروع؛ بر مبنای فاصلهٔ واقعی UTC |
| Daily | هر روز در ساعت محلی انتخاب‌شده، از تاریخ شروع به بعد |
| Weekly | در روزهای هفتهٔ انتخاب‌شده و ساعت محلی تعیین‌شده |

منطقهٔ زمانی صریح است؛ مثلاً `Asia/Tehran` یا `UTC`. پیش‌نمایش، offset را هم نشان می‌دهد. تاریخ شروع برای کار تکرارشونده، زودترین زمان مجاز است؛ ذخیرهٔ آن با تاریخ شروع گذشته باعث اجرای عقب‌افتاده‌ها نمی‌شود.

در تغییر ساعت فصلی، اگر خود زمان شروع وجود نداشته باشد فرم خطا می‌دهد؛ اگر یک موعد آیندهٔ روزانه/هفتگی وجود نداشته باشد، آن روز اجرا نمی‌شود. زمان محلی تکرارشده فقط در وقوع اول اجرا می‌شود. فاصله‌های ساعتی همچنان مدت واقعی را حفظ می‌کنند. پیاده‌سازی از [zoneinfo استاندارد Python](https://docs.python.org/3/library/zoneinfo.html) و دادهٔ زمانی سیستم استفاده می‌کند.

## کنترل و تاریخچه

- **Run now:** یک نوبت را همین حالا درخواست می‌کند؛ موعد معمول را جابه‌جا نمی‌کند. Task متوقف‌شده هم با این تأیید صریح قابل اجراست، مشروط به معتبر بودن مجوز و هدف‌ها.
- **Pause:** فقط نوبت‌های آینده را متوقف می‌کند. کار از قبل واردشده به صف یا در حال اجرا لغو نمی‌شود.
- **Resume:** از موعد آینده ادامه می‌دهد؛ عقب‌افتاده‌ها را جبران نمی‌کند. Task یک‌بارهٔ گذشته باید ابتدا ویرایش شود.
- **Edit:** دوباره از مراحل بازبینی می‌گذرد. نسخهٔ تعریف بالا می‌رود؛ اجراهای هنوز منتظر از تعریف قدیمی پیش از دسترسی شبکه رد می‌شوند. فرمانی که قبلاً ارسال شده برنمی‌گردد.
- **History:** با کلیک نام Task باز می‌شود. هر نوبت، زمان، علت/وضعیت و نتیجهٔ دستگاه‌ها را دارد. Open execution لاگ همان دستگاه و کنترل لغو موجود را باز می‌کند.

ارسال تکراری همان تأیید ساخت یا Run now، مورد جدیدی نمی‌سازد. با این حال اگر پاسخ یک عملیات قطع شد، ابتدا تاریخچه را ببین؛ ساختن درخواست جدید با شناسهٔ جدید یک اقدام جدا محسوب می‌شود.

## معنی وضعیت‌ها

| وضعیت | معنی |
|---|---|
| QUEUED / RUNNING | حداقل یک هدف در صف / در حال اجراست |
| SUCCESS | همهٔ اجرای هدف‌ها موفق گزارش شده‌اند؛ صحت اثر شبکه تابع عملیات و تست دستگاه است |
| PARTIAL | برخی هدف‌ها موفق و برخی ناموفق/لغوشده‌اند |
| FAILED | نوبت تمام شده ولی هیچ هدفی موفق نشده؛ نتیجهٔ هر هدف را بررسی کن |
| CANCELLED | همهٔ هدف‌ها لغو شده‌اند؛ لغو معادل rollback نیست |
| MISSED | موعد از مهلت ارسال عبور کرده؛ هیچ کار جبرانی وارد صف نشده است |
| SKIPPED_OVERLAP | نوبت قبلی همین Task هنوز در صف یا در حال اجراست |
| SKIPPED_CAPACITY | صف برای تمام دستگاه‌های این نوبت جا نداشته؛ هیچ‌کدام ارسال نشده‌اند |
| BLOCKED | صاحب Task، هدف، Credential یا Playbook دیگر معتبر نیست؛ Task برای بازبینی غیرفعال شده است |

مهلت ارسال ۶۰ ثانیه است. اگر سرویس مدتی خاموش باشد، برای بازهٔ ازدست‌رفته یک رکورد MISSED با اولین موعد جاافتاده ثبت و موعد به آینده منتقل می‌شود؛ برای هر ساعت/روز گذشته کار جداگانه تولید نمی‌شود. restart نزدیک موعد، داخل این مهلت، همچنان می‌تواند همان نوبت را ارسال کند.

کار ناموفق، نیمه‌اجرا یا با نتیجهٔ مبهم خودکار تکرار نمی‌شود. تشخیص وضعیت، صف و history از دیتابیس واقعی است؛ درصد پیشرفت ساختگی وجود ندارد.

## دسترسی‌ها

| نقش داخلی Narsika | دسترسی |
|---|---|
| Admin | ساخت Task، ویرایش/توقف/اجرای همهٔ Taskها و مشاهدهٔ پارامترهای آن‌ها |
| Operator | ساخت Task برای عملیات مجاز و مدیریت Taskهای خودش |
| Viewer | مشاهدهٔ خلاصه و تاریخچه؛ بدون ایجاد، تغییر یا اجرای Task و بدون دریافت متغیرهای خصوصی تعریف |

آپلود Playbook همچنان فقط با Admin است. مجوز صاحب Task پیش از ارسال و اجرای کار بررسی می‌شود. غیرفعال‌کردن حساب، انتقال به Viewer یا الزام تغییر رمز، اجرای خودکار آن حساب را متوقف می‌کند. تغییر معمول رمز باعث بی‌اعتبارشدن همیشگی Task نمی‌شود؛ کارهای از قبل صف‌شده همچنان نسخهٔ نشست ثبت‌شدهٔ خود را بررسی می‌کنند.

تغییر IP، پلتفرم، پورت SSH، پروفایل اتصال یا secret هدف و تغییر نسخه/محتوای Playbook نیازمند ویرایش و بازبینی Task است. تغییر نام ظاهری Credential به‌تنهایی هویت اتصال را عوض نمی‌کند. ذخیرهٔ Task باید با همان فهرست دستگاه‌های موردنظر بازبینی شود.

## اجرا، نصب و ارتقا

مرورگر لازم نیست باز بماند. همان سرویس Narsika و worker فعلی باید سالم و روشن باشند. زمان‌بند به cron، سرویس جدا، Redis، نصب Node یا ابزار خارجی وابسته نیست. ظرفیت فعلی ۲۰۰ تعریف Task و حداکثر ۳۲ دستگاه برای هر Task است؛ صف مشترک مجموعاً ۳۲ کار فعال/منتظر می‌پذیرد. تاریخچه صفحه‌بندی شده و خودکار پاک نمی‌شود.

ZIP را در پوشه‌ای تازه استخراج کن. برای نصب اصلی Ubuntu از پوشهٔ `narsika`:

```bash
bash run_linux.sh
```

برای ارتقای نصب موجود:

```bash
sudo narsika-admin backup
sudo narsika-admin upgrade /absolute/path/to/new/narsika
sudo narsika-admin doctor
```

پیش از ارتقا کارهای فعال را تمام یا لغو کن. دستور backup یک بکاپ دستی پلتفرم می‌گیرد؛ هیچ بکاپ روزانه یا نگه‌داری ۳۰روزه به‌صورت خودکار فعال نشده است.

روی Docker باید image جدید ساخته شود تا کد و بستهٔ `tzdata` را داشته باشد؛ فقط `--no-build` برای ارتقای سورس کافی نیست. راهنمای [Docker](DOCKER-START-FA.md)، [نصب انگلیسی](INSTALLATION.md) و [README](../README.md) همراه بسته هستند. Windows همچنان از `run_windows.bat` و مسیر Docker/WSL استفاده می‌کند.

## تغییرات فنی و حفاظت از داده

- سه جدول `scheduled_task`، `schedule_occurrence` و `schedule_run` اضافه می‌شوند؛ هیچ جدول، ستون، مدل، فایل، Route یا Playbook قبلی حذف نمی‌شود.
- پیش از افزودن جدول‌ها به دیتابیس موجود، snapshot رمزنگاری‌شدهٔ `narsika.db.before-schedules.sqlite3.enc` ساخته و صحت آن بررسی می‌شود. schema اصلی نسخهٔ ۲ باقی می‌ماند.
- ثبت نوبت، شناسهٔ یکتا، تمام کارهای هدف و تغییر موعد بعدی در یک تراکنش انجام می‌شود. شکست قبل از commit آن‌ها را نیمه‌ثبت‌شده باقی نمی‌گذارد.
- صف و قفل اتصال همان صف فعلی است. زمان‌بند فقط Backup یا Playbook به آن می‌سپارد و خودش فرمان تجهیزات نمی‌فرستد.
- نگه‌داری آفلاین، runهای دارای ارجاع از history زمان‌بندی را حذف نمی‌کند. این نسخه برای Task یا history حذف خودکار ندارد.
- تنها بستهٔ سیستمی افزوده‌شده `tzdata` است. نصاب native وجود دادهٔ زمانی را بررسی می‌کند و Docker آن را نصب می‌کند. dependency پایتونی، حساب سیستم یا سرویس جدیدی اضافه نشده است.

برای بازگشت به نسخهٔ قدیمی، ابتدا در نسخهٔ جدید همهٔ Taskها را Pause کن، صف را تخلیه/لغو کن و بکاپ کامل بگیر. سرویس را متوقف و از مسیر بازگردانی نسخهٔ سازگار استفاده کن؛ نسخهٔ قدیمی زمان‌بند را اجرا نمی‌کند و history جدید را نمی‌شناسد. از ابزار retention قدیمی روی دیتابیس جدید استفاده نکن. جدول‌های جدید را Drop نکن. snapshot را در صورت نیاز با ابزار restore موجود به یک مسیر آفلاین تازه بازگردان؛ نوشته‌های بعد از snapshot در آن وجود ندارند و باید جدا حفظ شوند.

## نتیجهٔ اعتبارسنجی

- تست کامل برنامه: ۲۵۳ تست موفق و یک skipped محیطی؛ شامل ۳۳ تست اختصاصی Schedules.
- حالات زمانی، Tehran/UTC، DST، دو dispatch هم‌زمان، idempotency، پرشدن صف، overlap، شکست تراکنش، snapshot ارتقا، نقش‌ها و تغییر هدف/Playbook بررسی شدند.
- worker واقعی داخل محیط ایزوله یک زمان‌بندی ذخیره‌شده را بدون مرورگر اجرا کرد؛ تماس تجهیزات در این تست با fixture جایگزین بود و هیچ دستگاه واقعی تغییر نکرد.
- HTTP واقعی Gunicorn، ورود، اجبار تغییر رمز، ۱۲ صفحه، API/assets و حفظ دستگاه و Task متوقف‌شده پس از restart موفق بودند.
- Python، ۱۳ ماژول JavaScript، shell، Compose و بارگذاری factory معتبرند. هر ۱۸ Playbook قبلی نیز دوباره syntax-check شد و معتبر بود.
- رندر و تعامل مرورگر در این نوبت تأیید نشده است؛ محدودیت دسترسی preview محلی در بررسی‌های قبلی ثبت شده بود. تست Node/HTTP جای آن را نمی‌گیرد.
- ساخت واقعی Docker، نصب تازه Ubuntu/Windows و اجرای زمان‌بندی روی Cisco/MikroTik واقعی در این محیط انجام نشده است.

فرمان‌های آزمون پس از آماده‌سازی محیط توسعه:

```bash
python -m pytest -q -rs
python -m pytest -q tests/test_schedules.py
python tools/validate_package.py
python tools/http_smoke.py
python tools/check_playbooks.py
```

برای اولین پذیرش روی Lab، یک Task بکاپ تک‌دستگاهی با موعد نزدیک بساز، مرورگر را ببند و پس از موعد نتیجه را بررسی کن. سپس Pause/Resume، restart قبل/بعد از موعد، دو هدف با نتیجهٔ متفاوت و تغییر Credential را آزمایش کن. Apply مستقیمِ صفحهٔ Firewall، cron آزاد و پشتیبانی Server جزو این مرحله نیستند؛ قابلیت‌های فعلی آن بخش‌ها حفظ شده‌اند.
